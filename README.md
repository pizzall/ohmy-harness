# ohmy-harness

把一个需要长时间思考、多步执行和反复验收的目标，交给一个持续运行的 AI 编程宿主。宿主担任主控，按每项工作所需的能力选择你授权的模型和工具，等待产物，独立验收。你回来时，可以看到交付了什么、按哪个版本验过，以及还有哪些决定需要你做。

## 什么时候值得用

**它最适合无人看守的长期复杂任务。** 例如，一次跨模块迁移要兼容旧数据、通过回归、更新文档。三个 Worker 各自报告完成，还不能回答“用户能否拿旧项目走完整条流程”。主控可以先组织一次最小的端到端迁移，用实际结果决定后续分工，最后在同一候选版本核对代码、数据与文档。

| 任务里遇到的事 | ohmy-harness 怎样处理 |
| --- | --- |
| 实现、读图和独立复核需要不同能力 | 按每项产物选择入口、模型与推理档。同一供应商的多个模型也可分别接单。 |
| 一个模型长时间没有返回 | 保留原尝试，核对会话和预期文件，能收回的产物继续送验，已就绪的独立工作继续推进。 |
| 多轮返工或上下文压缩后容易漏验 | 派单前冻结原件、方法和成功条件。审查 hook 核对逐项证据与候选版本，缺项保留待核验。 |
| 某条路线走不通 | 仍能验证原目标的路线可在授权内直接切换。需要降低或改变验收要求时，主控先向你确认。 |

无需守着每次轮询。主控宿主需要保持运行，模型调用受你已有的权限、用量和预算约束。关闭宿主后，可在新会话从账本续接。证据能否支持业务结论仍由审阅者判断。对一次问答或改一行代码这类工作，直接在宿主里完成通常更省事。

## 安装与第一次使用

准备 Python 3.11 或更高版本。技能目录自带账本，运行时只用 Python 标准库。Worker 可来自宿主的原生子代理，也可来自用户已配置、能非交互执行的 CLI。

**在 Codex 中安装**，向技能安装器给出公开分支下的技能目录，然后重新打开 Codex 会话。

```text
$skill-installer 安装 https://github.com/pizzall/ohmy-harness/tree/release/ohmy-harness
```

也可以手动克隆，将其中完整的 `ohmy-harness/` 子目录复制到宿主的用户技能目录。在 Codex 中，目标是 `$CODEX_HOME/skills/ohmy-harness/`，默认位置为 `~/.codex/skills/ohmy-harness/`。确认 `SKILL.md`、`references/` 和 `scripts/` 并列，其他项目即可按名称调用。

```sh
git clone --single-branch --branch release https://github.com/pizzall/ohmy-harness.git
```

打开目标项目，在新会话中给出可验收的目标。例如：

> $ohmy-harness 把导入器迁移到新格式。用同一份旧数据验证迁移前后的记录数和字段值，跑通一次完整导入，更新使用说明。最后给我候选版本、复跑命令和未通过项。

首次运行时，主控会核对可用 Worker。缺少资源清单时，它会询问你允许哪些入口和模型、哪些停用，并在项目中初始化审查 hook。资源清单和模型记忆保存在用户自己的 `~/.superagent/`，项目任务和证据索引保存在项目的 `.superagent/`。清单只需描述入口、能力与授权，凭据留给各工具原有的鉴权机制。

## 本地验证

在克隆的仓库根目录运行以下两条命令即可验证安装。初始化会在当前目录创建已被 Git 忽略的 `.superagent/`。实际工作时把 `--root` 指向目标项目。

```sh
python ohmy-harness/scripts/oma.py --root . init
python ohmy-harness/scripts/oma.py --root . status
```

`init` 会分别送入缺项和完整证据，审查 hook 成功拦住前者并放行后者才返回 `ready`。这两条命令只使用本地账本，无需模型订阅或 API Key。

需要了解具体的派单、恢复和验收规则，可从[技能入口](ohmy-harness/SKILL.md)、[超时恢复](ohmy-harness/references/05-recovery.md)和[审查放行](ohmy-harness/references/08-review.md)继续阅读。
