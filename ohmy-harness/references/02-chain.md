# 02　任务单、依赖与收件

## 2.1　把用户目标写成可派发的任务单

需求先落到用户可见的成功条件。先记录首选方案的收益、能力需求和验收项，再匹配入口，见[路由规则](03-routing.md)。已有有效结果或确定性检查直接复用，单产物且可整体验收时用一张任务单。多产物按各自验收边界拆分。

涉及多个产物时，写清一个能验证用户目标的关键使用场景和要保留的既有体验或行为。让验证该场景所需的任务尽早组成一个可验收版本。依赖该样板的后续任务待样板通过后，绑定已验收版本再派发。

| 字段 | 写什么 |
|---|---|
| 任务 ID、负责人 | 唯一任务 ID，当前 Worker 或宿主独占步骤的负责人 |
| 输入基线 | 项目根、提交或文件版本、授权范围 |
| 首选方案 | 改善的用户可见结果、所需能力、可观察的验收项 |
| 预期产物 | 可引用位置与版本标识方式 |
| 读写边界、依赖 | 可读和可写范围，必需输入的任务 ID、产物标识与版本 |
| 验收方法和停止条件 | 验收版本、命令或检查项、预算、超时、业务返工上限 |
| 派单选择 | 任务类型、难度、所需能力、所选入口、模型与推理档、选择依据；未知字段留空 |

共享契约可登记为独立且已验收的产物。书展首页中，页面布局和插画都消费尺寸、格式、移动裁切区域的契约 C1；组合验收消费页面与插画的真实产物。通用搜索图标可以直接复用。必要图片无法取得时标记组合视觉验收待办，页面布局、交互和报名表继续推进。

> 注：页面布局读取 C1 即可开工。把真实图片设为页面布局的必需输入，会让本可并行的两个任务互相等待。

## 2.2　判断就绪，再派发

1. 多任务派发前核对依赖指向有效任务与产物，检查成环和引用缺失。每个任务的必需输入均须按引用的版本通过验收；受阻任务登记原因。
2. 在就绪任务中选能同时运行的工作。写范围必须互斥，且宿主与各入口均有并发余量。并发写使用隔离工作树或输出目录；共享写入串行。记录实际执行区间用于核验是否并行。
3. 先登记任务 ID、尝试号、负责人、实际入口和工作区，再启动 Worker。拿到原生会话 ID 后按任务 ID 和尝试号补记；入口未提供则记录不适用。
4. 独立任务通过就解锁其可开工的下游。契约变更时查实际消费旧版的任务，更新依赖与验收版本，只重跑受影响的单项和组合检查。

使用随技能安装的 Python 账本时，主控可按以下顺序启动 Worker。

- 用 `DispatchTask` 登记尝试，`session` 传本次唯一的本地启动标识。账本命令返回后，由宿主在锁外并发启动 Worker。
- 得到原生会话 ID 后，可用现有 `RecordEvent` 按该尝试追加关联，将实际入口、起止时间、原生会话 ID 和可得用量写进事件。恢复时按任务与尝试号读取关联。
- 按尝试用 `SubmitResult` 收件、`Verify` 得出验收。派单前上面的依赖与容量由主控检查，`order_landing()` 用于集成顺序。

Python 直调 `DispatchTask(use_worker=...)` 也先把尝试写入账本，在锁外运行 Worker。执行期间可从另一调用读取 `scan`、处理独立任务，结束时按原尝试登记回包。

## 2.3　收件、验收、进度

- 回传包含候选版本、摘要、证据路径和未解决项。先核对任务与尝试号，再定位产物。没有可定位产物按失败处理。
- 在候选版本上复跑验收。业务失败带失败样例、预期、实际和目标版本，回原会话返工；环境失败、迟到结果与取消依[异常规则](05-recovery.md)处理。
- 验收、取消或确定失败后结算该独立任务。集成引用各必需产物的已验收版本，首个能覆盖关键使用场景的组合版本就绪后就复验。共享接口或库变化时复验受影响的组合。
- 单项通过但整体失败时，主控先记录用户可见的失败证据，再核对出问题的是哪项原要求、共享契约或计划假设。违反原任务单的产物回原会话修。计划假设失效时，调整受影响任务的顺序和依赖，更新计划记录，重新匹配待派和重开任务；仍有效的产物及独立工作继续。涉及用户目标或验收口径的取舍按[异常规则](05-recovery.md)请用户裁决。
- 汇报已验收叶子任务数 / 本轮叶子任务数，另列阻塞和集成状态。分母变化注明增减；撤回验收则减少分子。以可取回产物、可核查验收和阻塞解除更新进度。
- 交付产物、证据、仍受限的范围。需要续跑时写明目标、有效决定、任务 ID、候选或已验收版本、未完项及下一步，以同一宿主新会话回读。
